## Q1 实时性 —— 对方怎么"立刻"收到？

> PPT：HTTP 请求-响应是一问一答，服务端无法主动找客户端。必须建立一条服务端可以主动推数据的通道。

| # | 机制 | 文件 | 方法/位置 | 作用 |
|---|---|---|---|---|
| 1 | **开启 WS 支持** | `framework/config/WebSocketConfig.java` | 类上 `@EnableWebSocket` | 启用 WebSocket 功能 |
| 2 | **注册端点** | 同上 | `registerWebSocketHandlers()` L45 | 把 handler 挂到 `/ws/private` |
| 3 | **握手鉴权** | `framework/web/WebSocketHandshakeInterceptor.java` | `beforeHandshake()` | 校验 JWT，失败拒绝升级 |
| 4 | **连接建立** | `module/privatechat/websocket/PrivateWebSocketHandler.java` | `afterConnectionEstablished()` L52 | 登记在线表，下发 `connected` |
| 5 | **收报文分发** | 同上 | `handleTextMessage()` L70 | 按 type 路由到各处理方法 |
| 6 | **★主动推送出口** | 同上 | `send()` | `session.sendMessage()` 唯一出口 |
| 7 | **推送决策** | `service/PrivatePushService.java` | `pushMessage()` L59 | 查在线表 → 推本机 → 广播其他实例 |
| 8 | **前端建连** | `frontend/src/composables/usePrivateSocket.js` | `connect()` L127 | `new WebSocket(...)` |
| 9 | **前端接收** | 同上 | `ws.onopen` / `ws.onmessage` | 接收服务端推送 |

**一句话串起来**：
> 在 `WebSocketConfig` 注册 `/ws/private` → 客户端连上 → 服务端通过 `send()` 主动推 → 前端 `onmessage` 接收。

## Q2 可靠性 —— 消息会不会丢？

> PPT：网络随时断、进程随时崩。没有确认机制的消息等于没发。需要 ACK 确认 + 超时重发 + 去重兜底。

### 机制①：ACK 确认

| # | 文件 | 方法/位置 | 作用 |
|---|---|---|---|
| 1 | `PrivateWebSocketHandler.java` | `handleSendMessage()` **~L209** | 落库成功后 `send(PRIVATE_ACK, ack)` |
| 2 | `usePrivateSocket.js` | `handlePacket()` case `'private_ack'` **~L230** | 收到 ACK → `clearPending()` 停止重发 |

### 机制②：超时重发

| # | 文件 | 方法/位置 | 作用 |
|---|---|---|---|
| 3 | `usePrivateSocket.js` | `ACK_TIMEOUT` / `MAX_RETRY` **L55-56** | 3000ms / 3 次 |
| 4 | `usePrivateSocket.js` | **`sendWithRetry()` ~L363** | ★ 核心：发消息后挂 3s 定时器 |
| 5 | `usePrivateSocket.js` | `clearPending()` ~L354 | 收到 ACK 时清除定时器 |
| 6 | `views/chat/index.vue` | `submit()` | 调用 `sendWithRetry()` 而非裸 `send()` |

### 机制③：去重兜底

| # | 文件 | 方法/位置 | 作用 |
|---|---|---|---|
| 7 | `docs/mongo/init-private-chat.js` | `uk_client(senderId, clientMsgId)` | ★ 唯一索引 |
| 8 | `repository/PrivateMessageMongoRepository.java` | `selectByClientId()` | 重复时回查已有文档，不重复写入 |
| 9 | `service/PrivateMessageService.java` | `send()` **步骤③ ~L130** | 幂等前置判断，命中直接返回原记录 |

**一句话串起来**：
> 发送 → 挂 3s 定时器 → 服务端判重后落库 → 回 ACK → 客户端清定时器。
> 3s 没 ACK 就重发，服务端靠唯一索引保证不会重复。

**PPT 原话**：「重发与去重永远是一对，单写一个必出事」——**我们两个都写了。**

## Q3 顺序性 —— 先说的怎么排在后面？

> PPT：并发与重传会让消息乱序到达。"我走了"排在"我来了"之前是事故。需要会话内单调递增序号 seq。

### 服务端发号

| # | 文件 | 方法/位置 | 作用 |
|---|---|---|---|
| 1 | `service/MessageSeqService.java` | **`nextSeq()` L50** | ★ 核心：Redis INCR 原子发号 |
| 2 | 同上 | `SEQ_KEY_PREFIX` L32 | 键 `ai_tutor:seq:conv:{id}` |
| 3 | 同上 | `nextSeq()` 内部 | Redis 键丢失时按 `max(seq)+1` 重建 |
| 4 | `PrivateMessageService.java` | `send()` **步骤④ ~L139** | 调 `seqService.nextSeq(...)` |
| 5 | `PrivateMessageService.java` | `send()` **步骤⑤ ~L145** | `message.setSeq(seq)` 落库 |

### 数据库约束

| # | 文件 | 位置 | 作用 |
|---|---|---|---|
| 6 | `docs/mongo/init-private-chat.js` | `uk_conv_seq(conversationId, seq)` | 同会话 seq 唯一 |
| 7 | `docs/mongo/init-private-chat.js` | `createIndex` | 统一初始化 private_message 索引 |

### 客户端排序与补洞

| # | 文件 | 方法/位置 | 作用 |
|---|---|---|---|
| 8 | `usePrivateSocket.js` | **`trackSeq()` ~L290** | ★ 核心：空洞检测 |
| 9 | 同上 | `requestResync()` ~L323 | 发 `private_resync` 补洞 |
| 10 | `views/chat/index.vue` | `insertBySeq()` | 按 seq 升序插入，不用时间戳 |
| 11 | `PrivateWebSocketHandler.java` | `handleResync()` | 服务端返回缺失区间 |

**一句话串起来**：
> Redis INCR 发号 → 落库带 seq → 客户端按 seq 排序 → 发现跳号就请求补洞。

**为什么不用时间戳**：客户端时钟不可信（NTP 漂移、时区、人为改表）。

> PPT：对方不在线时消息必须先落库，上线后补投；同一账号多设备登录还要各端看到一致的历史。

### ② 上线补投（拉是兜底）

| # | 文件 | 方法/位置 | 作用 |

# 第二部分：通过日志查看实时聊天过程

## ⚠️ 先决条件：必须开启 DEBUG 日志

**当前状态**：私信模块有 **13 条 `log.debug`**，但 **Spring Boot 默认只输出 INFO 及以上**，
所以现在跑起来，这些日志**一条都看不到**。

### 开启方法

在 `backend/src/main/resources/application-dev.yaml` 末尾添加：

```yaml
# ========= 日志配置 =========
logging:
  level:
    # 私信模块：开启 DEBUG 才能看到连接、推送等关键流程
    com.edu.aitutor.module.privatechat: DEBUG
    # MyBatis：打印 SQL（application.yaml 已配 StdOutImpl，这里控制级别）
    com.edu.aitutor.module.privatechat.mapper: DEBUG
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [%thread] %-25logger{25} - %msg%n"
```

**改完重启后端生效。**

## 实操：完整观察一次发消息

### 第 1 步：准备

| 步骤 | 操作 |
|---|---|
| 1 | 改 yaml 加 DEBUG 配置 |
| 2 | 重启后端 |
| 3 | 浏览器开两个窗口（无痕模式开第二个） |
| 4 | 学生登录 `/chat`，教师登录 `/chat` |

### 第 2 步：观察连接建立（Q1）

IDEA 控制台应该看到：

```
10:23:01.234 DEBUG [io-8082-exec-1] c.e.a.m.privatechat.websocket.PrivateWebSocketHandler - 私信连接建立，userId=7，sessionId=abc123
10:23:05.456 DEBUG [io-8082-exec-2] c.e.a.m.privatechat.websocket.PrivateWebSocketHandler - 私信连接建立，userId=1，sessionId=def456
```

**说明**：两个人都连上了，WebSocket 通道已建立。

### 第 3 步：发一条消息（观察 Q2 + Q3 + Q4）

学生发消息后，控制台会按顺序出现：

```
① ==>  Preparing: INSERT INTO private_message (... seq ...) VALUES (..., ?, ...)
    ==> Parameters: 1(Long), 6(Long), 7(Long), 1(Long), "你好"(String), ...
    <==    Updates: 1                                    ← 【Q3】seq=6 会话内递增
                                                          ← 【Q4】消息已落库
② ==>  Preparing: UPDATE private_conversation SET last_message_id = ?, ... 
    <==    Updates: 1                                    ← 更新会话摘要

（对方在线，无 warn 日志 = 推送成功）
```

**如果对方离线**，会看到：

```
10:23:10.789 DEBUG ... PrivatePushService - 接收方离线，跳过推送，receiverId=1，messageId=10
```

**这条日志就是 Q4 的直接证据**——消息没推出去，但已经落库了。

### 第 4 步：验证 Q2 重发机制

**方法 A：断网测试**

1. F12 → Network → 选 `Offline`
2. 发一条消息
3. 观察：界面显示"发送中"，3 秒后自动重发
4. 恢复网络 → 收到 ACK → 变成"已发送"

**方法 B：看重复提交日志**

在 Network 面板按住消息重发，或者在代码里手动调两次相同的 `clientMsgId`：

```
10:25:01.123 DEBUG ... PrivateMessageService - 消息重复提交，返回原记录，messageId=9
```

**这就是去重在起作用**——第二次没有新建消息，返回了已有的。

### 第 5 步：验证 Q4 离线补拉

| 操作 | 预期日志 |
|---|---|
| 1. 关掉教师页面 | `私信连接关闭，userId=1，code=1000` |
| 2. 学生发 2 条消息 | 每条都有 `接收方离线，跳过推送` |
| 3. 教师重新打开 `/chat` | `私信连接建立，userId=1` |
| 4. 紧跟一条 SQL | `SELECT ... FROM private_message WHERE receiver_id = 1 AND id > ...` |

**第 4 步的 SQL 就是 `sync` 补拉在工作**——教师登录后自动拉取离线期间的消息。

## 日志级别说明（答辩可讲）

| 级别 | 本项目用在哪 | 说明 |
|---|---|---|
| **DEBUG** | 连接、推送、判重等正常流程 | 量大，只在排查时开 |
| **INFO** | （建议补充）消息落库 | 关键业务节点，生产可开 |
| **WARN** | 可恢复异常（离线跳过、并发冲突） | 需要关注但不影响功能 |
| **ERROR** | （本项目未用） | 严重故障 |

**设计原则**：不是所有日志都重要。DEBUG 打开时日志量很大，生产环境只开 INFO。

## 常见问题排查表

| 现象 | 看哪条日志 | 说明 |
|---|---|---|
| 页面显示"实时在线"但收不到消息 | `接收方离线，跳过推送` | 对方真离线，或 Redis 在线表异常 |
| 消息一直"发送中" | 无 `private_ack` | 服务端没回 ACK，检查后端是否报错 |
| 消息出现两条 | `消息重复提交` 应该出现 | 若没有，说明去重失效，查唯一索引 |
| 顺序乱了 | SQL 里的 `seq` 值 | 检查 seq 是否连续（1,2,3...） |
| 重连后消息丢失 | 是否有 `SELECT ... id > ?` | 没执行说明 `sync` 没发出来 |
| Redis 异常 | `Redis 发号失败，回退数据库基线` | 服务降级了，功能仍可用 |

## 建议补充：给 seq 加一条 INFO 日志

目前 **seq 分配没有日志**，但它是 Q3 的核心。建议在 `PrivateMessageService.send()` 步骤⑤后面加：

```java
// 【Q3 顺序性】记录发号结果，便于验证 seq 连续递增
log.info("消息落库 conversationId={} seq={} messageId={}",
         conversation.getId(), seq, message.getId());
```

**这样即使不开 DEBUG，也能在默认日志里看到 seq 变化。**
